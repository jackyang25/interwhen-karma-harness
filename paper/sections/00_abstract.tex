Verifier-guided reasoning (interwhen-style) intercepts an LLM's intermediate
reasoning steps and asks an external verifier to approve them before they
take effect. We evaluate this mechanism in a clinical decision-support
setting --- specifically, \emph{procedural input verification} of tool-call
payloads against patient facts extracted from case vignettes --- using
medical\_calculator\_eval ($N=1066$) and Qwen3-30B-A3B-Thinking-2507 as the
primary model. The verifier compares each (field, value) pair the model
proposes to dispatch to an MCP medical calculator against a reference set
of facts extracted from the case by Sonnet 4.6.
Across four pre-registered primary contrasts (Bonferroni $\alpha=0.0125$),
no verifier configuration significantly improved over the no-verifier
baseline. In exploratory analyses, combining a tool-forcing system prompt
with the verifier (B$'$+E) actively reduced accuracy by 9.0 percentage
points (McNemar $p < 10^{-15}$, 118 correct$\rightarrow$wrong vs 22
wrong$\rightarrow$correct). A flag-composition diagnostic traced this
harm to the upstream \emph{fact extractor}, not to the verifier's
comparison logic: a single field (sex) accounted for $\sim$32\% of all
verifier flags under upfront full-schema extraction. A follow-up condition
replacing upfront extraction with per-tool-call focused extraction
\emph{partially} validated the schema-size hypothesis --- the sex
fraction fell to 13\%, the correct-rate on intervention rows doubled
(14\%$\rightarrow$24\%), and total token cost dropped $\sim$57\% --- but
accuracy did not significantly recover (+1.9 pp, $p=0.103$). We conclude
that in clinical settings where the verifier's reference must be
LLM-extracted from free-text input, the binding constraint on
verifier-guided reasoning is the reference pipeline, not the verifier.
Schema-size is one contributor but not the sole bottleneck; deployment
should validate the extractor on the relevant field set before adopting
intermediate-verification machinery.
